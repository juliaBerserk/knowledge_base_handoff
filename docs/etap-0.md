# Этап 0 — договорённости и план

Дата: 2026-10-30. Клиент: **React + TypeScript (Vite)**.
Клиентский стек подтверждён пользователем на этапе 0.

Этап 1 уже создал production-каркас. `sample_docs/` сохраняется как
обезличенные фикстуры для тестов.

## Зафиксировано ТЗ (не менять без согласия)

- Одна организация. Три пространства: личное, должность, отдел.
- Единица обмена — материал или запись. «База коллеги» = только опубликованное.
- Статусы: черновик → на проверке → опубликовано → в архиве. Проверка руководителем — настройка.
- Роли: сотрудник, руководитель отдела, HR, администратор, аудитор ИБ. Преемник — назначение, не роль.
- Администратор не видит содержимое знаний в приложении и в БД.
- Очистка до записи в БД и до LLM. Исходный файл не хранится.
- Стек: Python 3.12, FastAPI, Pydantic v2, PostgreSQL 16 + pgvector, SQLAlchemy 2, Alembic,
  воркер через таблицу `jobs`, Embedder (BGE-M3), LLMClient (OpenAI-compatible), Argon2id, Natasha,
  React + TS (Vite), Docker Compose + Nginx (TLS), pytest, Ruff, Playwright, GitHub Actions.
- Не использовать: LangChain, LlamaIndex, Celery, Redis, микросервисы, Kubernetes, дообучение.

## Клиент

SPA в `frontend/`: React 18+, TypeScript, Vite.

- Сообщения UI на русском.
- Сессия — cookie HttpOnly; CSRF-токен в заголовке с клиента.
- Вопрос-ответ — SSE (`EventSource` или `fetch` + ReadableStream).
- e2e — Playwright по основным сценариям (с этапа 12, каркас с этапа 1).

API — JSON под префиксом `/api/`. Nginx в Compose отдаёт SPA и проксирует API.

## Окружение и эксплуатация

- Секреты только в переменных окружения / Docker secrets. `.env` в `.gitignore`.
- Один стек Docker Compose на одной ВМ. Хостинг и бэкапы — на территории РФ (это условие
  внедрения, не проверка в коде).
- Часовой пояс по умолчанию: `Europe/Moscow`.
- SMTP не обязателен: приглашение копируется администратором. Если заданы `SMTP_*` —
  письмо отправляется с STARTTLS. Реализация — этап 3.
- Первый администратор создаётся CLI-командой bootstrap; она выводит одноразовую ссылку
  в консоль, но не устанавливает и не показывает пароль. Детали — [docs/etap-3.md](etap-3.md).
- Auth: интерфейс провайдера + локальная реализация; OIDC/LDAP остаются будущим этапом.

### Предварительная схема данных

Схема будет вводиться последовательными миграциями Alembic; это план, не
предварительно созданные таблицы:

- Оргструктура и доступ: `departments`, `positions`, `users`,
  `employment_assignments` (включая даты, активную должность и роль).
- Аутентификация: `invitations` (только хэш токена и срок действия),
  `credentials` (только Argon2id-хэш), `sessions`, `totp_credentials`.
- Аудит: `audit_events` (append-only, только тип события, субъект, объект и
  безопасные метаданные).
- Знания: `materials` и версии очищенного текста, `redaction_events` (тип и
  количество, без исходных значений), `chunks` (текст, `tsvector`, embedding),
  `knowledge_records`, `record_sources`.
- Рабочая очередь и RAG: `jobs`, `chats`, `chat_messages`, `answer_feedback`.
- Эстафета: `handoffs` и `handoff_checklist_items`.

Связи, ограничения, индексы и RLS будут проектироваться в этапе, который вводит
соответствующие таблицы. Должность и отдел не будут подменяться идентификатором
сотрудника. Копия записи хранит ссылку на оригинал и автора; синхронизации нет.
Доступ администратора к содержательным таблицам не выдаётся на уровне БД.

### Предварительная карта API

Все прикладные маршруты находятся под `/api/`; текущий `GET /api/health`
сохраняется. Точные схемы запросов и ответов утверждаются перед реализацией
каждого этапа:

- Auth/admin: `/api/auth/*`, `/api/admin/users*`.
- Оргструктура и текущий пользователь: `/api/departments`, `/api/positions`,
  `/api/me`.
- Материалы и публикация: `/api/materials*`, `/api/records*`,
  `/api/build-jobs*`.
- Поиск и чат: `/api/search`, `/api/chats*`, потоковый `/api/chats/{id}/answer`.
- Эстафета и аудит: `/api/handoffs*`, `/api/audit*`.

Это границы планирования, не контракт для обхода единой проверки прав:
авторизация выполняется до чтения данных и до поиска, RLS остаётся второй
линией защиты.

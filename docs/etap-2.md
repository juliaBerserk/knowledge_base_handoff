# Этап 2 — оргструктура, роли и права

## Результат

- Добавлены отделы, должности, учётные записи и история назначений.
- Проверка публикации для нового отдела включена по умолчанию и задаётся на
  уровне отдела.
- Права на знания вынесены в чистый доменный модуль. Перевод на другую
  должность закрывает доступ к старым должностным материалам, не меняя их
  авторство.
- PostgreSQL RLS ограничивает чтение оргданных по роли и отделу. Роль
  `estafeta_app` не владеет таблицами и не имеет `BYPASSRLS`.
- `app.user_id` устанавливается в начале транзакции через транзакционный
  `set_config`, эквивалентный `SET LOCAL`.
- Неаутентифицированные API для просмотра оргструктуры не добавлялись.

## Таблицы миграции `0002_org_access`

- `departments`: название и настройка `publication_review_required`.
- `positions`: должность принадлежит отделу, не сотруднику.
- `users`: ФИО, нормализованная корпоративная почта, роль и признак активности.
- `employment_assignments`: история связи сотрудника с должностью; частичный
  уникальный индекс гарантирует не более одного текущего назначения.

Удаление связанных записей ограничено внешними ключами; пользовательские
тексты и материалы знаний в этой миграции отсутствуют.

## Единые права

`backend/estafeta/domain/access.py` предоставляет `can_read`, `can_write`,
`can_submit_for_review` и `can_publish`.

- Личное пространство читается и изменяется только владельцем.
- В должностном пространстве черновик доступен автору при текущем назначении;
  материалы на проверке доступны руководителю отдела, опубликованные —
  сотрудникам должности и отдела.
- Пространство отдела — представление опубликованных материалов должностей
  отдела и доступно только сотрудникам этого отдела; изменять его напрямую
  нельзя.
- При включённой проверке автор отправляет свой черновик на проверку, а
  руководитель того же отдела публикует запись. При отключённой проверке автор
  может опубликовать собственный черновик.
- Архив и личные данные других пользователей не открываются по ролям HR,
  администратора или аудитора ИБ.

RLS применён к оргструктуре и профилям: сотрудники читают собственный профиль,
руководители — сотрудников своего отдела, HR и администратор — профили в
рамках своих полномочий. Изменять пользователей и оргструктуру через БД может
только администраторский контекст приложения.

## API и запуск

Новых HTTP-маршрутов нет: `GET /api/health` остаётся единственным маршрутом.
Защищённые `/api/me`, `/api/departments` и `/api/positions` добавляются после
реализации входа и сессий.

Миграция применяется штатным сервисом Compose:

```powershell
docker compose up --build
```

Для локального тестирования backend:

```powershell
cd backend
py -3.12 -m pip install -e ".[dev]"
ruff check estafeta tests alembic/env.py alembic/versions
pytest -q
```

RLS интеграционно тестируется при `RUN_DB_TESTS=1` с PostgreSQL: тесты должны
подключаться приложением ролью `estafeta_app`, а подготовку фикстур и миграции
выполнять ролью `estafeta_owner`.

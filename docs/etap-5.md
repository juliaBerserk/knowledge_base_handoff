# Этап 5 — журнал аудита

Миграция `0005_audit` создаёт `audit.events`. В событии хранятся время БД,
тип действия, результат и UUID участника и объекта, если они известны.
У журнала нет текстовых полей для паролей, содержимого документов, токенов
приглашений, кодов TOTP, адресов или тела запроса.

- Входы фиксируются с результатом. При неудачном входе введённый логин
  в журнал не записывается. Срабатывание лимита входа фиксируется один раз
  для клиента за минутное окно.
- Журналируются выход, установка и смена пароля, включение TOTP, подготовка
  доступа первому администратору, выпуск приглашения и успешное чтение чужого
  объекта через репозиторий знаний. Выпуск ссылки и её доставка по SMTP могут
  завершиться по-разному, поэтому событие фиксирует именно выпуск ссылки.
- Добавление события и соответствующее изменение в БД проходят в одной
  транзакции. Типы событий для загрузки, публикации, копирования, экспорта и
  запросов к ИИ подготовлены. Их записи добавляются при реализации операций.

Прикладным ролям выдана вставка только полей события. PostgreSQL назначает
время и идентификатор. Триггер блокирует `UPDATE`, `DELETE` и `TRUNCATE`.
Автоматического удаления нет, поэтому записи хранятся как минимум год.
Откат ревизии блокируется, если в журнале есть записи. Учётные данные
роли миграций остаются у оператора БД.

## Чтение

`GET /api/audit/events` доступен с действующей сессией аудитора ИБ.
Параметр `limit` принимает значения от 1 до 100, по умолчанию 50.
`action` фильтрует по типу события. Значение `next_before_id` из ответа
передаётся как `before_id` для следующей страницы. Ответы не кэшируются.
Графический интерфейс относится к этапу 12.

Для применения миграции запустите `docker compose up --build`. Отдельные
переменные окружения для аудита не требуются.

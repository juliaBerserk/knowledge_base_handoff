# Этап 3 — аутентификация

Ревизия `0003_auth` создаёт таблицы `auth.credentials`, `auth.invitations`,
`auth.sessions` и `auth.rate_limits`. Прикладная роль получает доступ к этим
таблицам и трём полям справочника сотрудников — UUID, почте и роли.

## Приглашение и восстановление

Первого администратора создаёт оператор БД командой из [README](../README.md).
Повторный вызов меняет приглашение, пока пароль первого администратора ещё
не задан. Для существующего сотрудника администратор с настроенной 2FA
выпускает ссылку по UUID через интерфейс или HTTP API. При настроенном
`SMTP_*` администратор может отправить её на корпоративную почту. Сотрудники
без корпоративной почты входят по UUID, который отображается после установки пароля.

Ссылка действует 72 часа. В базе остаётся только хэш токена. Новая ссылка
заменяет предыдущую. Успешная установка пароля погашает токен и отзывает
старые сессии. При восстановлении сохраняется ранее настроенная 2FA.
Пароль содержит от 16 до 256 символов. Можно сочетать кириллицу, латиницу,
цифры и специальные символы. Пароль проверяется по списку распространённых
паролей из Django 5.2. Список и его лицензия входят в пакет приложения.
Для хранения пароля используется Argon2id.

## Сессии и TOTP

Сотрудник самостоятельно меняет пароль раз в месяц в разделе «Учётная запись».
Он вводит текущий пароль и дважды вводит новый. После смены все прежние сессии
и неиспользованная ссылка восстановления аннулируются. Соблюдение срока
контролируют руководители. Система не отслеживает срок и не отправляет напоминания.

Cookie сессии имеет флаги `HttpOnly`, `Secure`, `SameSite=Lax`. Сессия истекает
через 30 минут простоя или 12 часов после входа. Значения настраиваются.
Защищённые POST принимают `X-CSRF-Token`, связанный с текущей сессией.
Обработчики аутентификации проверяют `Origin` при его наличии и принимают JSON.

Пять неверных паролей или кодов блокируют новые попытки на 15 минут.
Отдельные лимиты по IP действуют для входа, активации и подтверждения TOTP.
Воркер периодически удаляет просроченные записи аутентификации.

Администратор и руководитель отдела на первом входе получают доступ только
к настройке TOTP и выходу. Подтверждение TOTP отзывает старые сессии и выдаёт
новую. Секрет TOTP хранится в зашифрованном виде. Повтор кода уже принятого
временного интервала отклоняется. Пароль можно восстановить ссылкой.
Восстановление доступа при утрате TOTP потребует отдельной процедуры.

## Маршруты под `/api/auth`

- `POST /redeem` — задать пароль по ссылке.
- `POST /password/change` — самостоятельно сменить пароль после входа.
- `POST /login`, `GET /session`, `POST /logout` — управление сессией.
- `POST /totp/start`, `POST /totp/confirm` — привязать аутентификатор.
- `POST /invitations/{employee_id}` — выпустить ссылку для сотрудника.

Постоянная блокировка учётной записи с отзывом сессий реализована в
`auth.service.block_account`. Вызов по последнему рабочему дню относится
к этапу эстафеты. Локальный вход выделен в провайдер. Для подключения OIDC
или LDAP предусмотрен отдельный контракт внешнего провайдера.

Для проверки первого входа в браузере подготовьте отдельную тестовую БД и
передайте свежую ссылку bootstrap в `E2E_BOOTSTRAP_URL`. В каталоге `frontend`
выполните `npm run test:e2e -- e2e/auth.spec.ts`. Для установленного Chrome
задайте `E2E_BROWSER_CHANNEL=chrome`.

# Этап 13 — эксплуатация и приёмка

Обновление с этапа 12 применяет миграцию `0012_chunk_visibility`. Политика
PostgreSQL проверяет ту же пару из идентификатора материала и хэша текста,
используя выборку, которую планировщик может хешировать. Ограниченная функция
поиска возвращает только идентификаторы из разрешённой области и поддерживает
планы с GIN и HNSW. API читает итоговые фрагменты под ролью приложения с RLS
и повторной проверкой прав. Роль администратора не может вызывать функцию.
[Политики строк PostgreSQL](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)
[Фильтрация HNSW в pgvector](https://github.com/pgvector/pgvector#filtering)

## Резервные копии PostgreSQL

Выполняйте команды из корня репозитория на хосте с Docker Compose, Python 3.12 и
`age`. Доступ к Docker и ключам восстановления нужен выделенному оператору
инфраструктуры. Роль администратора приложения остаётся без доступа к знаниям.
Оператор хранит резервные копии и выполняет восстановление на территории РФ.

На защищённом хосте сгенерируйте ключ получателя. Разместите файл
`estafeta-recovery.age-key` в защищённом хранилище с доступом только для оператора
восстановления. Передайте на сервер резервирования файл `recipients.txt` с
открытым ключом. Имена файлов и каталоги в командах приведены для примера.

```bash
umask 077
age-keygen -o estafeta-recovery.age-key
age-keygen -y estafeta-recovery.age-key > recipients.txt
```

На сервере создайте защищённый каталог для копий. Укажите фактическое имя
запущенного проекта Compose, которое показывает `docker compose ls`.

```bash
python scripts/backup.py --project-name estafeta --env-file .env.production backup \
  --directory /srv/estafeta/backups --recipients /srv/estafeta/recipients.txt
```

Скрипт шифрует поток `pg_dump` до записи на диск и публикует файл `*.pgdump.age`
после успешного завершения обеих команд. Копия содержит схему, знания, журнал
аудита, очередь jobs и учётные записи. При восстановлении потребуется заново
войти и перевыпустить неиспользованные приглашения. Для работы TOTP сохраните
исходный `APP_SECRET_KEY` в хранилище секретов отдельно от архива. Отдельно
храните конфигурацию, сертификаты и редактируемые правила очистки.
[Документация pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html)
[Документация age](https://github.com/FiloSottile/age/blob/main/doc/age.1.ronn)

Интервал копирования, срок хранения копий, допустимую потерю данных и время
восстановления согласует организация. Проверяйте код возврата и появление
свежего файла, переносите зашифрованную копию в отдельное хранилище и
периодически проводите контрольное восстановление. Журнал аудита хранится
в БД с политикой append-only. Эксплуатационная политика должна обеспечивать
доступность записей за период не менее года.

## Восстановление

Возьмите копию из доверенного хранилища. Подготовьте новый проект Compose
с отдельным томом и файлом окружения. Начните с той же основной версии PostgreSQL
и совместимой версии pgvector. Настройте уникальные пароли ролей в
`.env.recovery` и исходный `APP_SECRET_KEY`. Файл окружения держите
вне репозитория либо в защищённом каталоге с ограничением доступа.

Запустите только `db`. Контейнер создаст роли и расширение при инициализации
пустого тома. Запускать миграции до восстановления не требуется.

```bash
docker compose -p estafeta-recovery --env-file .env.recovery \
  -f docker-compose.yml -f docker-compose.tls.yml up -d --wait db
python scripts/backup.py --project-name estafeta-recovery --env-file .env.recovery restore \
  --archive /srv/estafeta/backups/selected.pgdump.age --identity /secure/estafeta-recovery.age-key
```

Скрипт проверяет целостность шифротекста и применяет архив одной транзакцией.
Существующие схемы приложения служат причиной отказа. Владение объектами,
выданные права и политики RLS восстанавливаются из архива. Роли и их пароли
создаются при инициализации нового тома.

После восстановления запустите миграции до версии развёртывания. На закрытом
стенде проверьте вход, чтение опубликованного знания от сотрудника, отсутствие
доступа к нему у администратора, аудит и состояние незавершённых jobs.
Запишите фактическое время восстановления перед переключением пользователей.
Решение о переключении принимает оператор компании.
[Документация pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html)

Автоматическая проверка создаёт два временных проекта PostgreSQL, делает
копию и проверяет отказ для повреждённого файла, перенос данных и аудита,
отсутствие старых сессий, восстановление RLS и ограничений администратора.
Для запуска нужны зависимости backend, Docker и `age`.

```bash
python deploy/tests/backup_smoke.py
```

## Нагрузочная приёмка

Поднимите отдельный стенд с БД `estafeta_acceptance` на пустом томе,
проинициализируйте роли Compose и примените Alembic. Укажите
`DATABASE_OWNER_URL` и `DATABASE_URL` тестового стенда для Python-процесса.
Задайте те же `AUTH_PUBLIC_ORIGIN`, `APP_SECRET_KEY`, `EMBEDDING_MODEL` и
`EMBEDDING_REVISION`, которые использует приложение на этом стенде.
Для полной приёмки запустите Nginx с доверенным сертификатом, API, воркер,
BGE-M3 и настроенную LLM. Используйте только тестовые данные.

```bash
mkdir -p data
python scripts/acceptance.py --manifest data/acceptance-sessions.json seed
python scripts/acceptance.py --manifest data/acceptance-sessions.json measure \
  --origin "$AUTH_PUBLIC_ORIGIN"
```

Фикстура создаёт 300 учётных записей, 100 000 чанков в 1000 материалах двух
отделов и 50 новых документов для сборки. Синтетические 1024-мерные векторы
нагружают индекс. Качество поиска по рабочим документам проверяйте отдельно
на обезличенном корпусе. Файл сессий содержит действующие токены тестовых
аккаунтов. Ограничьте доступ к каталогу и удалите файл после прогона. Для
повторного полного прогона используйте новый тестовый том.

Перед нагрузкой сценарий прогревает приложение и проверяет векторную выдачу
по фразе без совпадений FTS. Сценарий печатает время прогрева, p95, максимум
и долю запросов с векторной выдачей. Он
проверяет HTML и поиск за 2 секунды при 20 одновременных сессиях, отсутствие
выдачи из закрытого отдела, первую отображаемую цитату SSE за 5 секунд и
завершённую сборку всех 50 документов за 10 минут. Служебное событие SSE
`started` не считается началом ответа. Полный прогон требует векторную
выдачу в каждом поисковом запросе. `--core-only` выполняет диагностику HTML
и API поиска с отдельным отчётом о доле семантических запросов.

Дополнительно замерьте готовность рабочего экрана в браузере. Запускайте из
`frontend/`, указав абсолютный путь к файлу тестовых сессий.

```bash
E2E=1 E2E_BASE_URL="$AUTH_PUBLIC_ORIGIN" \
  E2E_ACCEPTANCE_MANIFEST=/absolute/path/to/data/acceptance-sessions.json \
  npm run test:e2e -- e2e/acceptance.spec.ts
```

Для Firefox задайте `E2E_FIREFOX=1`. Для Chrome и Edge используйте
`E2E_BROWSER_CHANNEL=chrome` и `E2E_BROWSER_CHANNEL=msedge` соответственно.
Для Яндекс Браузера укажите путь к установленному исполняемому файлу в
`E2E_BROWSER_EXECUTABLE`. В протокол приёмки внесите ресурсы и расположение
стенда, версии моделей и браузеров, результаты замеров и восстановления.

### Локальный результат

На Windows с PostgreSQL 16 и pgvector в Docker, локальным API и тестовым
эмбеддером максимум составил 0,060 с для HTML и 0,920 с для поиска.
При 20 одновременных сессиях все 20 запросов вернули векторную выдачу,
поисковая выдача из закрытого отдела отсутствовала. Рабочий экран Chrome
прошёл порог 2 с. Полную приёмку с BGE-M3, LLM, сборкой 50 документов, Яндекс
Браузером и корпоративным сертификатом проводят на стенде компании.
